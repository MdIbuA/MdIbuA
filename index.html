P—01

ML platform · Infosys Springboard internship

CryptoPulse

A crypto forecasting platform that shows how accurate its forecasts are, not just the forecast line.

  • Python
  • TensorFlow / Keras LSTM
  • scikit-learn
  • FastAPI
  • MongoDB
  • React + Vite
  • Binance API
Source on GitHub (opens in a new tab)
Read the case study

Problem

Crypto forecasting dashboards usually show a confident line with no way to judge it. I wanted a platform where every forecast came with the metrics needed to decide how much to trust it.

Approach

  • Ingestion: OHLCV candles from the Binance REST API, paginated past the 1,000-row limit, with a CSV fallback if the API fails.
  • Features: moving averages (12/24/168 h hourly; 7/14/30/50 d daily), returns, rolling volatility, price range, high/low ratio, volume MA.
  • Models: a stacked LSTM (128→64→32 units, L2, batch-norm, dropout) trained in notebooks; scikit-learn Gradient Boosting (multi-output) for the 7/15/30-day horizons served by the API.
  • Serving: FastAPI with JWT auth and MongoDB (Motor); retrains a cached daily model when it is over 7 days old or the data has shifted by more than 10%.
  • Interface: React + Recharts dashboard with per-horizon RMSE/MAE/R² and SMA, EMA, Bollinger and RSI overlays.

My role

Built during the Infosys Springboard AI internship (Batch 5). I am the sole committer on the public repository.

Results

On a chronological 80/20 split for BTC, the LSTM reached R² 0.94 and RMSE ≈ $5,049 on close price. Direction accuracy was 47.9% for close and 57.8% for open.

Limitations & lessons

The high R² mostly reflects persistence: tomorrow’s price is close to today’s. Near-50% direction accuracy means the model has no reliable trading edge, and the platform should not be used for trading decisions. The biggest lesson was to report direction accuracy next to R² from the start, because R² alone flatters price models.

P—02

LLM agent · Take-home engineering task · 2026

Supermarket Ops Agent

A neighbourhood store run entirely through Telegram chat: billing, stock, credit ledgers and GST invoices, all driven by Claude calling tools.

  • TypeScript
  • Anthropic SDK
  • PostgreSQL
  • Prisma
  • grammY
  • Docker Compose
  • Vitest
Source on GitHub (opens in a new tab)
Read the case study

Problem

Small Indian stores track inventory, bills and customer credit (khata) on paper. The brief: make the chat itself the product, with no dashboard or admin panel.

Architecture

A hand-written agent loop on the Anthropic SDK, capped at 15 rounds. Claude picks from 32 typed tools across inventory, billing, khata, analytics, documents and preferences. Each tool validates its input and returns structured results. All business data comes from PostgreSQL through tools, so the model never makes up prices or stock.

Hard parts

  • Money: stored as integer paise; GST (CGST/SGST split) computed deterministically with Decimal.js.
  • Overselling: atomic conditional update — … WHERE quantity >= $1 — returns a structured error the model explains.
  • Concurrency: serializable isolation and row locks on bill finalization.
  • Idempotency: processed Telegram update IDs are recorded; re-finalizing a bill returns the existing result.
  • Real artifacts: PDF invoices (pdfkit) and PPTX analysis decks with charts (pptxgenjs).

Why no agent framework

The loop is about 50 lines. Owning it directly gave full control over tool execution, retries and round limits, and made it easy to reason about.

Limitations

Single store per bot, no real payment processing, text-only input, and conversation history held in memory (business data persists in Postgres).

P—03

Serverless GenAI · AWS Builder Center weekend challenge · Aug 2026

DocuMind AI

Upload a PDF; get a summary, answers grounded in the document, entity extraction, tone analysis, two-document comparison and an exportable report.

  • Amazon Bedrock (Nova Pro)
  • AWS Lambda · Python 3.12
  • S3 + CloudFront
  • React + Vite
Source on GitHub (opens in a new tab) Published write-up on AWS Builder Center (opens in a new tab)
Read the case study

Architecture

A React SPA on S3 behind CloudFront talks to a Python Lambda. Lambda extracts text with pypdf, builds a task-specific prompt, and asks Bedrock’s Nova Pro for strict JSON so the frontend can render structured results. IAM roles scope access to Bedrock and S3. A mock mode lets the frontend run locally without an AWS account.

How answers are grounded

The extracted document text goes straight into the prompt (about 12–14k characters, depending on the task), and the model is told to answer from that text. There is no vector index; this is “long-context stuffing”, not retrieval.

Limitations & next steps

Long documents get truncated, so answers can miss later sections. Scanned PDFs have no text layer and are not OCR’d. The natural next step is chunking plus embedding retrieval, with citations back to page numbers.

02

How I work

I’m drawn to the space between a model that works in a notebook and a product someone can use.

Most of my projects cross that gap end to end. In CryptoPulse, the same codebase pulls market data, trains models, serves them through FastAPI and charts them in React. In the Supermarket Ops Agent, the hard problems weren’t prompts. They were paise-precise money, row locks and idempotent message handling.

My default is to start with the failure modes. What happens when the API is down, when the model invents a price, when two bills finalize at once? Then I write the limitations next to the results, because a 0.94 R² means little without a 48% direction accuracy beside it.

Outside coursework I build in public through cloud weekend challenges and stay close to developer communities as an AWS Student Builder Campus Leader and a Microsoft Learn Student Ambassador. Next, I want to work on production AI systems where reliability, evaluation and cost matter as much as the model.

  1. 01Ground the model in real data; never let it invent facts.
  2. 02Measure honestly, including the metric that makes you look worse.
  3. 03Prefer boring, owned code over a framework you can’t debug.
